## 2. 外层 shield（条目 1、3）

```text
P      = u32be(1) + u32be(app_id) + u32be(1)
       + u32be(len(build)) + u32be(len(device_id)) + u32be(16)
       + build + device_id + digest16
blob   = u32be(4 | (token_type << 16)) + u32be(1)
       + u32be(len(P)) + u32be(len(P)) + RC4(key, P)
shield = "XY" + base64(blob)
```

- RC4 key 是 `.rodata:0x13d9e` 的 ASCII 串，13 字节（把 abort 消息串复用为密钥）。样本内检索即可定位，属**静态可见常量**。
- 曾疑似的魔数 `35 16 11` 就是 RC4 密钥流前三字节（`P` 前三字节为 0 直接透出），不是 AES-ECB 标志。
- 已否定的假设：HMAC-SHA 系、SHA-384、AES-ECB。

## 3. 定制 HMAC-H（条目 2）

结构由三个函数的参数与输出长度确定：`0x7f224` 取 token payload 前 64 字节（外层 key），`0x7feec` 吸收请求字节，`0x8001c` 输出 16 字节。

```python
K64    = token_payload[:64]
inner  = H(bytes(a ^ 0x36 for a in K64) + request_bytes)
digest16 = H(bytes(a ^ 0x5c for a in K64) + inner)
```

`H` 是定制 MD5 族变体，与标准 MD5 的差异点已逐项定位：

| 项 | 差异 | 值 |
| --- | --- | --- |
| IV | 逆序存储 | `[0x10325476, 0x98badcfe, 0xefcdab89, 0x67452301]` |
| K16 | 篡改 | `0xf6002500` |
| K19 | 篡改 | `0xe90001aa` |
| K29 | 篡改 | `0xfc010010` |
| K39 / K40 | 互换 | — |
| K41 / K42 | 互换 | — |
| 第 63 轮 | 以块入口上下文状态作累加器 | 不同于标准 MD5 |
| c63 | **不进摘要** | — |

验证脚本对零块、内层 `D1`、外层 `D2` 三组向量断言：

```

inner_digest  0333710ea360d55803703522349e1a88
outer_digest  91653d232769b94c0a97c334119f2da0
vectors=3 mismatches=0
```

## 4. type 6/7 会话变换（条目 4、5、6、8）

### 4.1 函数签名与数据范围

`0x50010(payload_ptr, 64, key_ptr, 20, out_ptr)`：

| 量 | 大小 | 说明 |
| --- | --- | --- |
| 输入 payload | 64 字节 | 会话 token 材料 |
| 输入 key | 20 字节 | 标记为 type 6（或 type 7 带时间字节） |
| 输出 | 16 字节 | 4 个小端 32 位字 |

输出确实取决于 key：key[0]=0x00 得 `1bd84c72f2a5819e348c0f3c8876f0d0`，key[0]=0xFF 得 `8dd6a7a0d8c2e96c9017de4fe9f6fbe4`（相同全零 payload）。故 key 是**真实输入**，不是占位。

调用点（`0x46a14`）：type 6 走 `0x50010` 后接 `0x5a128(out, timeByte, w21)`；type 7 的 `time(NULL)` 低字节作为额外入参。结果以 `0x28`（`(`）长度前缀写回 `std::string`（16 字节 + NUL），失败路径写 0x20 个空格。

### 4.2 算法构成（静态普查结论）

对 `0x50010`..`0x5a264`（41 556 字节 / 10 389 条指令）做指令普查：

| 检查 | 结果 |
| --- | --- |
| AES / SHA1 / SHA256 / SHA512 / SM3 / SM4 / CRC32 / PMULL 指令 | **各 0 条** |
| rodata 对象引用 | **29 个 .rodata 对象被引用**（16 个字节序列表 + 13 个常量对象） |
| 索引式表查找（`tbl`/`tbx`/`ld1 {vN.16b}` 查表） | **0 处**；区域内的表引用**全部**是整块向量加载（`ldr qN` 16 字节 / `ldr dN` 8 字节），无按字节下标访问 |
| 常量生成方式 | 大常量 `movz` + `movk` 内联；同时**存在** rodata 常量块供向量指令直接加载 |
| 与已知常量表匹配（区域内） | MD5 T 表、SHA-1 K、SHA-256 K **在区域内 0 命中** |

> **本节曾发布过一条错误结论**（“rodata 常量表引用 0 处”）。该结论源于一个有缺陷的操作数匹配器：它用 `adrp` 目标寄存器名去子串匹配整条操作数串，既漏掉 `add` 产生的基址，也把 `ldr qN,[base,#imm]` 这类向量块加载整体跳过。修正过程分两步：`re/xyass_tabscan3.py`（补上 `add` 基址与向量块加载，带动手自检）先找回了被整体跳过的 `ldr qN` 引用；随后的 `re/xyass_tabscan4.py` 采用**写寄存器即失效**的寄存器精确跟踪，剔除了 v3 因寄存器复用而产生的假阳性。下表为 v4 结果。

#### 4.2.2 动态可达性（决定性证据）

静态引用只说明“有代码指向它”。为排除“死代码 / 只被邻接函数引用”，在 Unicorn 中对真实 `0x50010` 调用挂了 `.rodata` 读钩子，逐访问记录 `(地址, pc)`：

| 输入 | 触达的 .rodata 对象 |
| --- | --- |
| 全零 payload + 全零 key | 16 个字节序列表**全部**（各 1 次）+ 13 个常量对象 |
| `(17i+3)` payload + 全零 key | 仅 13 个常量对象（走单块快路径） |
| `0x00..0x3f` payload + `0x00..0x13` key | 16 个字节序列表**全部** + 13 个常量对象 |

结论：

- 字节序列表与常量块**都是热路径数据**，不是死数据。
- 每个字节序列表在一次调用中**只被整块读取一次或零次**（16 字节表由两次 8 字节加载覆盖），且**没有任何一条指令对它做下标寻址**。实测该路径下 `.rodata` 访问共 88 次、全部为 **8 字节**加载、来自 30 个不同 PC，**字节大小（size=1）的 `.rodata` 访问为 0**；区域内 `tbl`/`tbx` 为 0，寄存器件址访存的目标全是栈或 GOT。
- 因此这 16 张表**不构成 S 盒式查找层**：它们是**常量向量池**，每张表 16 字节作为 128 位立即数参与 SIMD 运算，而不是被 key 索引。这一点与“无索引式表查找”的静态结论一致，两者互相印证。

#### 4.2.3 区域内**未**引用的相关常量（避免误读）

`.rodata` 中确实存在具名密码学常量，但**区域不引用**，必须与本区域的常量集分开陈述：

| 地址 | 内容 | 区域外引用方 | 本轮确认程度 |
| ---: | --- | --- | --- |
| `0x15ca0` | 四个 IV 字的**倒序**排列 `76 54 32 10 fe dc ba 98 89 ab cd ef 01 23 45 67`（即 D,C,B,A） | `0x81978` | **已确认**：`0x81978` 是 **定制 H 的 init**，由 `0x81930`／`0x81954` 以 K 表 `0x94a10` 调用（见 §3）——属本报告的摘要链路，不是无关的标准 MD5 |
| `0x15d40` | 四个 IV 字的**标准内存序** `01 23 45 67 89 ab cd ef fe dc ba 98 76 54 32 10`（LE 字序 A,B,C,D） | `0x4c0c8` | 用途未定：该函数同时读取 `0x15d40` 与 SHA-1 常量，疑为多哈希辅助；本轮未追踪其调用者，故**不断言**其为“标准 MD5/SHA-1 实现” |
| `0x15e70` | SHA-1 `H4 = 0xc3d2e1f0` | `0x4c0c8` | 同上 |
| `0x15000` 起 | libc++ `demangle`/`__cxa_` 字符串区（紧邻常量池之前） | — | 本区域**不引用**；该区线性排布在常量池之前，容易与常量池混为一谈 |

> `0x15ca0` 与 `0x15d40` 是同一 IV 的两种字节序，分属两条不同链路（定制 H 的 init 与 `0x4c0c8`）。这也修正了上一版把 `0x15ca0` 描述为“标准 MD5 IV”的措辞——它服务的是定制 H。

至此，§4.2.1 的 16 张表 + 13 个常量对象 = 29 个引用对象，与§4.2.2 动态钩子命中的对象**完全一致**；此前版本中出现过的 `0x15000`（字符串区）与 `0x94710` 一族（定制 H 的 K 表）都是邻接或误判，不属本区域。

比对扫描另发现：完整 **MD5 T 表（64 个轮常量，256 字节）以原始小端数据存在于 `.data:0x94710`–`0x9480f`**，其后紧邻另一张 256 字节相似表（`0x94810` 起，64 槽中仅 6 槽与标准 MD5 T 相同），再往后是 `0x94910`、`0x94a10` 两张各自 3/64 匹配的派生表——与上游 [algorithm.md](../algorithm.md) 的「摘要与会话」节（type 1–5 描述符 `0x91928` 起、K 表 `0x94710`/`0x94810`/`0x94910`/`0x94a10`）一致——本轮独立复算得到同一组地址与匹配率。**这些表位于 type-6 区域之外，本区域对其 0 引用。**

> **扫描器精度提示**：仅凭 `adrp` 建立的页地址做长时间跟踪会把“寄存器早已被覆盖”的情况也算作引用，从而产生大量假阳性。例如把 `[x19,#0x150]` 这类**结构体字段访问**误判为对 `0x94710` 的引用，一次就能虚报出 285 个“引用点”。本报告采用的判据是**写寄存器即失效**的寄存器精确版本（`re/xyass_tabscan4.py`）；上表中 16 张表与 13 个常量对象的引用均由该版本复核，且与 `.rodata` 读钩子的动态命中一一对应，两套独立方法结果一致。

SHA-1 K（`0x5a827999` 等）与 SHA-256 K 在整个 `.so` 的**任何位置都不以原始数据或立即数形式出现**（全文件原始数据检索 + 全部可执行段立即数检索均为 0 命中），说明本样本未内置未混淆的标准 SHA-1/SHA-256 轮常量表。

出现的运算族为（括号内为区域内条数）：`add`(2037)/`sub`(440)/`eor`(192)/`orr`(62)/`orn`(4)/`eon`(8)/`and`(56)/`cmp`(173)/`csel`(160)/`cset`(42)/`tst`(10)；`ror`(56)/`lsr`(29)/`lsl`(10)/`ushl`(6)/`bfi`(7)/`bfxil`(4)/`ubfx`(5)/`rev64`(2)/`ext`(2)；`mul`(61)/`madd`(3)/`msub`(3)/`udiv`(3)/`neg`(5)；`mov`(1477)/`movi`(2)/`dup`(1)/`umov`(4)/`st1`(3)。区域共 53 种助记符。

直接调用的外部函数只有 1 个：`bl 0x8aed0`（PLT 桩，5 处调用）。

### 4.3 16 个按索引绑定的字节置换器（`0x59f84`–`0x5a124`）

这是一组以 16/20/28 字节为单位的叶子函数，**全部逐条读出，不存在未解部分**。统一形态：

```asm
add  x8, x0, w1, uxtb        ; x8 = x0 + (byte)i
ldrb w9, [x8]                ; w9 = x0[i]
mov  w10, #<const>           ; 常量（部分变体没有这一步）
<op> w9, w9, ...             ; 见下表
strb w9, [x8, #0x14]         ; x0[i + 0x14] = 结果
ret
```

即：以调用方给出的字节下标 `i`（`w1`）为唯一索引，把 `x0[i]` 经常量与下标混合后写入 `x0[i+0x14]`（偏移 20）。**不读密钥、不做表查找**，因此是完全可枚举的置换层。

| 地址 | 大小 | 常量 | 运算序列 |
| ---: | ---: | ---: | --- |
| `0x59f84` | 28 B | `0x69` | `eor` → `orr` |
| `0x59fa0` | 28 B | `0x53` | `eor` → `orr` |
| `0x59fbc` | 28 B | `0x69` | `orr` → `orr` |
| `0x59fd8` | 28 B | `0x69` | `and` → `orr` |
| `0x59ff4` | 28 B | `0x53` | `and` → `orr` |
| `0x5a010` | 28 B | `0x53` | `orr` → `orr` |
| `0x5a02c` | 28 B | `0x96` | `eor` → `eor` |
| `0x5a048` | 28 B | `0x96` | `orr` → `orr` |
| `0x5a064` | 28 B | `0x96` | `orr` → `eor` |
| `0x5a080` | 28 B | `0x35` | `eor` → `orr` |
| `0x5a09c` | 28 B | `0x35` | `eor` → `and` |
| `0x5a0b8` | 28 B | `0x35` | `eor` → `orn` |
| `0x5a0d4` | 20 B | — | `orn`（`orn w9, w1, w9`） |
| `0x5a0e8` | 20 B | — | `orn`（与 `0x5a0d4` 字节级等价） |
| `0x5a0fc` | 16 B | `0xff` | 无读改写，直接写常量 |
| `0x5a10c` | 28 B | `0x35` | `eor` → `orn` |

两条可直接复核的混淆细节：

- `0x96` 恰是 `0x69` 的按位取反（`~0x69 & 0xff = 0x96`）；`0x5a02c`/`0x5a048`/`0x5a064` 与 `0x59f84`/`0x59fbc` 构成互补变体对。
- `0x5a0d4` 与 `0x5a0e8` 行为完全一致，是刻意填入的重复体。

这类“同一语义多份实现 + 变体常量”是该区域的基本混淆手法，也解释了为什么只按行为聚类会低估函数数量。

### 4.4 状态字节派生与分派器（条目 5、8）

每轮进入算法块前，状态机执行：

```asm
; 0x55b2c                    ; 0x55b58
ldrb w9, [x20]               and  x9, x9, #3
...                          ; 0x55b5c
                             stp  x9, x10, [x29, #-0x28]   ; 存 {选择子, 表基址}
```

随后 `0x557c4` 读回并 `0x557d8` 执行 `ldr x8,[x8,x9,lsl #3]; blr x8`，其中表位于 `0x91868`，8 个条目对应 8 个块：

| 选择子 | 目标 | 选择子 | 目标 |
| ---: | --- | ---: | --- |
| 0 | `0x55b64` | 4 | `0x552f0` |
| 1 | `0x569c8` | 5 | `0x58858` |
| 2 | `0x57320` | 6 | `0x590a0` |
| 3 | `0x580dc` | 7 | `0x5980c` |

**这 8 个块都是独立的完整函数**（各有自己的栈帧与保护字 `mrs x8,tpidr_el0; ldr x16,[x8,#0x28]`），不是同一函数的轮内联展开。该跳转表由 `.rela.dyn` 重定位填充（8 个槽的 addend 逐一确认），不是加密数据。

选择子 `x9` 是 `[x20] & 3` 的一个字节，而 `x20` 是**栈上帧**（本次实测 `x20=0x6fffef40`，payload/key/输出分别在 `0x50000000/0x50000400/0x50000800`），因此**这个**选择子不直接来自 payload/key 缓冲区，而是状态机自身算出的块索引。因此“选择子由 payload 决定 ⇒ 算法随数据变化”是**误读**。

但必须同时说明一个更重要的、由动态实测得出的事实：**该 8 项表只是第一层分派器之一**。区域共 **504 处** `br`/`blr` 间接跳转；而**实际执行到**的间接跳转目标是其子集，且随输入变化。逐输入精确统计（`re/xyass_blkchain4.py`）：

| 输入（payload / key） | 指令数 | 间接跳转次数 | 进入的顶层块 |
| --- | ---: | ---: | --- |
| 全零 / 全零 | 39 251 | 2 765 | `0x552f0` `0x57320` `0x580dc` `0x590a0` `0x5980c` |
| `(17i+3)` / 全零 | 4 889 | 283 | `0x552f0` `0x55b64` `0x569c8` `0x590a0` `0x5980c` |
| `0x00..3f` / 全零 | 39 249 | 2 765 | `0x552f0` `0x57320` `0x580dc` `0x590a0` `0x5980c` |
| 全零 / `0x00..13` | 42 717 | 2 859 | `0x569c8` `0x57320` `0x580dc` `0x58858` `0x590a0` `0x5980c` |
| `0x00..3f` / `0x00..13` | 42 708 | 2 861 | `0x552f0` `0x57320` `0x580dc` `0x590a0` `0x5980c` |

表中前 4 组输入合计触达 **241 个**不同间接目标；扩大到 10 组（含随机输入）后合计 **337 个**。进一步把输入集合扩到 **2 000 组**后，转移关系进入**饱和**：**404 个** site、**750 条**转移边、**409 个**目标，最后 500 组仅新增 1 条边（§4.6.1）。

8 个顶层块的进入频次并不均等——只有 2 个在全部 10 组输入中都被进入，其余 6 个各只覆盖一部分输入：

| 顶层块 | 命中输入数 | 顶层块 | 命中输入数 |
| --- | ---: | --- | ---: |
| `0x590a0` | 10 / 10 | `0x580dc` | 5 / 10 |
| `0x5980c` | 10 / 10 | `0x55b64` | 6 / 10 |
| `0x552f0` | 7 / 10 | `0x57320` | 4 / 10 |
| `0x569c8` | 7 / 10 | `0x58858` | 3 / 10 |

其中 `0x58858` 在这 10 组样本中**恰好只出现在 key 非零的 3 组输入**（`zero/rampkey` 与两组 `rand`），是一条可复核的样本相关性；但样本量不足以断言它是 key 的判据，故仅作观察记录，不上升为结论。

“块选择由数据驱动”的确定证据是上表本身：同一段代码在不同输入下进入的块集合、总指令数与间接跳转次数均不同（283 → 2 861）。

结论修正为：**控制流确实随输入变化**（进入的块集合、总指令数、间接跳转次数都不同），这是任何含数据相关分支的真实算法的正常表现；CFF 在此基础上进一步把**等价**路径随机化。此前“等价语义不变、路径随机化”的说法只描述了一半——正确表述是：**块选择由数据相关条件驱动，而 CFF 使同一语义有多条等价路径**。

这也解释了为什么单条 trace 的符号化 lift 无法泛化：一条记录只覆盖该输入走过的那条路径（见 §4.4 的控制流实测）。

### 4.5.1 输入-输出字节依赖矩阵（实测）

逐字节翻转（`payload_i ^= 0xFF`、`key_i ^= 0xFF`，基线 `payload=0x00..0x3f`、`key=0x00..0x13`），观察 16 个输出字节中哪些发生变化：

| 方向 | 有影响的输入字节 | 受影响的输出字节 |
| --- | --- | --- |
| payload → out | **64 / 64 全部** | **16 / 16 全部** |
| key → out | **20 / 20 全部** | **16 / 16 全部** |

结论：`0x50010` 对 64 字节 payload 与 20 字节 key 是**全域扩散**的——没有任何输入字节是装饰性的，也没有任何输出字节只依赖单一输入子集。这同时排除了“部分字节未参与运算”的可能。

### 4.6 CFF 控制流的两条定性结论（含对上一版的纠正）

本节回答两个不同的问题，二者结论**相反**，必须分开陈述：

| 问题 | 结论 | 手段 |
| --- | --- | --- |
| 转移关系是否**有限**（能否建成有限自动机） | **是**——已饱和 | 2000 组输入执行覆盖（§4.6.1） |
| 单条 trace 的符号电路能否**泛化** | **否** | 跨输入预测 4/4 mismatch（§4.6.3） |

> **纠正上一版的一条错误论证。** 上一版（`deepdive/README.md` §57、`audit.md`）曾把 `0x50010` 的统一闭式列为“**原理上不可能**”，依据是“504 个间接分支中 0 个常量目标 ⇒ 有限状态机 lift 不可能”。这条论证**不成立**，本轮已撤回：
>
> 1. **数值错误**——所谓“213 个表加载 / 291 个索引加载”的分类，来自一个**不健全**的扫描器（`re/xyass_cfgfinite.py`）：它把被分析窗口内**任意**一条 `ldr` 记为“依赖表加载”，**并未做 def-use 追踪**判断该 `ldr` 是否真的流向分支寄存器。仅需一例即可证伪：`0x500fc` 处的 `br x9`，其 `x9` 来自 `0x5008c ldr x9,[x20,#0x590]`，是**重定义后**被 `0x500b4 add x9,x9,x3` 覆盖的旧值；但该窗口内另有一条 `0x500b0 adrp x5,#0x53000` 未被计入，扫描器只因看到 `0x5008c` 的 `ldr` 就归为 `table-load`。
> 2. **推论错误**——即便“目标取自运行时表”成立，也只能推出“**离线静态**重建需要解析表内容”，与“有限自动机不可能”无关。本轮用重写的 def-use 分析（`re/xyass_cfg_defuse.py`）复核：504 个间接分支中**可达的 404 个**全部由 `add Xd, base, wOff` 形式产生，`base` 来自 `.data` 槽位加载；这**恰恰是**“有限状态机 + 运行期填充的转移表”的结构，而不是“不可判定”。

#### 4.6.1 转移关系有限：2000 组输入的饱和实测（决定性）

`re/xyass_cfg_saturate.py` 对 2 000 组混合输入（随机 / 常量 / 结构化）逐组记录**每个被执行到的 `br`/`blr` 的实际目标**，统计 `(site → target)` 边集合的增长：

| 输入数 | 边数 | 触达 site 数 |
| ---: | ---: | ---: |
| 200 | 693 | 384 |
| 800 | 713 | 388 |
| 1 400 | 749 | 404 |
| 1 600 | 750 | 404 |
| 1 800 | 750 | 404 |
| 2 000 | 750 | 404 |

**最后 500 组输入：边 +1，site +0。** 转移关系**已经饱和**。饱和后的完整结构：

| 指标 | 值 |
| --- | ---: |
| 触达的间接分支 site | **404** |
| 不同转移边（site → target） | **750** |
| 不同的目标地址 | **409** |
| 目标地址范围 | `0x50100` – `0x5a10c` |
| 落在 `0x50010`–`0x5a264` 之外的目标 | **0** |
| 未按 4 字节对齐的目标 | **0** |
| 单 site 最大出度 | **16** |
| 出度 ≥ 2 的 site | 110 |

出度直方图（出度 → site 数）：`1→294, 2→38, 3→11, 4→28, 5→3, 6→26, 16→4`。

出度 16 的 4 个 site 正是 `x0[i]` → `x0[i+0x14]` 的索引置换器（`0x53fc8`/`0x53fe4`/`0x54000`/`0x54030`），其目标即 §4.3 列出的 16 个字节置换器 `0x59f84`–`0x5a10c`，**与静态跳转表的 16 个槽位逐一对上**。

**结论**：`0x50010` 的控制流是一个**有限转移系统**——404 个状态（间接分支点）、750 条转移边、单点出度 ≤ 16。上一版“有限状态机 lift 不可能”的说法**与实测相反**，已撤回。完整转移表见 `re/xyass_cfg_transitions.txt`（404 行，格式 `site n_targets target…`）。

#### 4.6.2 转移表为何无法只靠静态文件读出

静态可读的跳转表只有两处：

| 表 | 位置 | 槽位 | 内容 |
| --- | --- | ---: | --- |
| 置换器分派表 | `.data.rel.ro` `0x917e8`–`0x91860` | 16 | `R_AARCH64_RELATIVE` 指向 16 个字节置换器 `0x59f84` `0x59fa0` `0x59fbc` `0x59fd8` `0x59ff4` `0x5a010` `0x5a02c` `0x5a048` `0x5a064` `0x5a080` `0x5a09c` `0x5a0b8` `0x5a0d4` `0x5a0e8` `0x5a0fc` `0x5a10c`（**全部 REACHED**） |
| 算法块分派表 | `.data.rel.ro` `0x91868`–`0x918a0` | 8 | 指向 `0x55b64`/`0x569c8`/`0x57320`/`0x580dc`/`0x552f0`/`0x58858`/`0x590a0`/`0x5980c` |

两表在 `.rela.dyn` 中**连续排布**（`0x917e8`–`0x918a0` 共 24 槽），前 16 槽为置换器、后 8 槽为算法块。

但**驱动 404 个 site 的大多数表不在文件里**。实测（`re/xyass_cfg_tables.py`、`re/xyass_cfg_memstatic.py`）：

- 每个 site 的目标形如 `target = base + K`，其中 `base` 由 `ldr xR,[xM,#disp]` 从 `.data` 槽位（`0x933a8`、`0x93520`、`0x93580`、`0x93588`、`0x93590`、`0x935c0`、`0x935e0`、`0x945c8` 等）取出，`K` 为 `movz`/`movk` 立即数或 `sxtw` 偏移；
- 这些 `.data` 槽位**在文件镜像中全为 0**（`0x93590` 文件值 `0000000000000000`），只在模块加载/重定位后才有值；指向的堆区在 `Full()` 构造完成后仍 `UNMAPPED`；
- 16 个槽位的取值在 3 次**全新模拟器实例**中逐字节一致，即**确定性的**，但**不可从文件静态读出**；
- `re/xyass_cfg_memstatic.py` 对 3 组输入的逐访问比对显示：区域内代码读取的字**与文件镜像不同**（例：`0x5008c` 读 `0x93590`，模拟器值 `0x38864a8`，文件值 `0x0`）。**因此“表的静态枚举”在文件层面不成立**，必须经由一次真实加载/重定位。

#### 4.6.3 单 trace lift 为何不能泛化（仍成立）

`re/xyass_lift50010.py` 把**一条**执行记录逐步提升为符号电路，`re/xyass_type6_ref.py` 用它预测；修正对比宽度后（原脚本把 16 字节结果与 20 字节 `std::string` 缓冲比较，属实现缺陷）实测 `vectors=4 match=0 mismatches=4`。

原因即 §4.6.1 的实测事实：**同一 site 在不同输入下会走向不同目标**（110 个 site 出度 ≥ 2，单点最多 16 个目标），单条 trace 只固化了它走过的那一条边。这不是“不可判定”，而是“**需要按 site 记录转移集合**”。

#### 4.6.4 当前判定（可达性已闭环，选择谓词未符号化）

- **可达性层面：已闭环。** 404 个 site、750 条转移边、409 个目标全部枚举并落盘（`re/xyass_cfg_transitions.txt`），覆盖 2 000 组输入的饱和结果；无区域外目标、无不齐目标。
- **转移选择函数层面：未闭合。** 每个 site 在多个目标之间**按什么条件**选择（即 `K` 作为输入的函数的闭式表达），尚未给出。这需要把控制流合并进数据通路一起符号化，或对 750 条边逐边求路径谓词。
- 因此本节把上一版的“**原理上不可能**”**降级为“尚未符号化的转移谓词”**：问题可判定、状态与边均已枚举，缺的是逐 site 的选择谓词，而非原理性障碍。

| 操作 | 样本数 | 输出翻转位均值 | 区间 |
| --- | ---: | ---: | --- |

接近理想的 64/128，且双侧扩散（payload 与 key 均强影响），与“分组混合 + 混淆轮”的结构一致。

## 5. Tiny 高熵区（此前的误判已纠正）

`libtiny.so` 的 `.data` `0x754AC0`–`0x7701C0`（112 384 字节，香农熵 ≈ 7.9982945）曾是“加密 WASM blob”的候选。经三路独立验证：

| 检查 | 方法 | 结果 |
| --- | --- | --- |
| 是否有代码把它当地址引用 | 汇集区域内所有 `adrp`/`add` 目标 | **0** |
| 是否有立即数指向该区 | `mov`/`movz` 立即数扫描 | **0** |
| 是否有重定位项加数落区 | `.rela.dyn` 加数扫描 | **0** |

（`0x754AC0` 区域内容 SHA-256 = `706dbd99b5d75c8ba5529a538f8e9ae86fe4a355d6c7fb39a1c454dbefb4ff62`；脚本对含重定位段与不含重定位段的两种口径都跑了，合计 0 命中。）

相关误读也一并纠正：`0xf7b80` 是普通字符串常量拷贝，`0x4948A8` 是 `adrp/add/ldr` 序列，`0x53296C` 是 `memcpy`。

**正确表述**：样本中**未发现静态或已覆盖动态路径引用的高熵数据区**。既不能称其为“加密 WASM”，也不能称其为“设备绑定白盒密文” ——没有任何引用方，也没有解密调用者。

## 7. 本轮 CFF 结论的复现命令

以下脚本位于逆向工作副本 `re/`（不随仓库发布），均以模拟器加载真机样本 `libs/lib/arm64-v8a/libxyass.so`
（SHA-256 `8e7db9e41ec7cacaf504fa07e68a325aa1bae220cabb5a745d31e3154922a17b`）后执行，**不使用任何线程钩子做逐指令回放**：

```bash
# 1. 转移关系饱和实测：2 000 组输入，逐 site 记录真实目标
python3 re/xyass_cfg_saturate.py     # -> re/xyass_cfg_saturate.json / .txt
python3 - <<'PY'                     # -> re/xyass_cfg_transitions.txt（404 行转移表）
import json
d=json.load(open('re/xyass_cfg_saturate.json'))
e={int(k,16):sorted(v) for k,v in d['edges'].items()}
open('re/xyass_cfg_transitions.txt','w').write(
  "\n".join("%#08x %2d %s"%(s,len(t),' '.join('%#x'%x for x in t)) for s,t in sorted(e.items()))+"\n")
PY

# 2. 递归 def-use：每个 br/blr 的目标到底由什么产生
python3 re/xyass_cfg_defuse.py       # -> re/xyass_cfg_defuse.json

# 3. 转移表来源与确定性
python3 re/xyass_cfg_tables.py       # 16 个 .data 槽位取值，跨 3 次全新实例一致
python3 re/xyass_cfg_memstatic.py    # 区域内访存 vs 文件镜像（证明静态不可读）
python3 re/xyass_cfg_siteindex.py    # 逐 site 出度（110 个 ≥ 2，最大 16）
```

判读要点：

- `xyass_cfg_saturate.txt` 的**最后 500 组输入**增量为 `edges +1 / sites +0` ⇒ 转移关系饱和；
- `xyass_cfg_transitions.txt` 不含 `0x50010`–`0x5a264` 之外的目标，也不含非 4 字节对齐目标；
- `xyass_cfg_defuse.json` 中 `CONST-ONLY` 计数为 **0**，但这**不构成**“有限状态机不可能”的论据（原因见 §4.6）。
